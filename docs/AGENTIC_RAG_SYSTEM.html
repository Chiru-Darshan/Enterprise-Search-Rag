📊 System Overview

SearchUnify Agentic RAG is an end-to-end Retrieval-Augmented Generation system that combines:

  • Web Crawling — Discovers and extracts content from websites
  • Hybrid Search — Combines BM25 (keyword) + vector (semantic) retrieval
  • Reranking — Cross-encoder models re-score results by relevance
  • LLM-Powered QA — Generates grounded answers with citations
  • Semantic Verification — Fact-checks claims against source documents
  • Corrective Loop — Retries with query rewrites if verification fails
🎯 Key Innovation: This system doesn't just retrieve and answer—it verifies every claim is grounded in actual document text, and rewrites queries to find missing evidence if initial retrieval was weak.

⚙️ Data Pipeline & Lifecycle

Phase 1: Data Ingestion & Indexing

1

Web Crawling

The web crawler discovers URLs from sitemap.xml, fetches pages (with JS rendering for dynamic content), extracts clean main content, and stores as JSONL documents.

Output: data/searchunify/documents_*.jsonl — one document per line, with metadata (title, URL, section, breadcrumbs).

2

Content Chunking

Documents are split into overlapping chunks (default: 700 tokens, 200-token overlap) to fit within model context windows and capture semantic boundaries.

Output: data/searchunify/chunks_*.jsonl — preserves parent doc URL, title, section, and chunk text.

3

Vector Embedding & Indexing

Each chunk is embedded using bge-small-en-v1.5 (384-dim vectors) and indexed into OpenSearch with both BM25 (keyword) and dense_vector fields for hybrid search.

Index: searchunify_chunks — ~150M+ document corpus ready for millisecond-scale retrieval.

Phase 2: Query-Time Pipeline

User Query ↓ [Retrieval Agent] ├─ Hybrid search: BM25 + semantic ├─ Top-K results (default: 10) └─ Raw relevance scores ↓ [Reranking Agent] ├─ Cross-encoder scores: (query, doc) → [0, 1] ├─ Sort by rerank score (descending) └─ Top-N reranked (default: 3-5) ↓ [Answer Agent] ├─ Build context from reranked chunks ├─ LLM generates answer with inline citations [1], [2]... └─ Citations linked to source URLs ↓ [Verification Agent — Semantic Check] ├─ Extract cited sentences from answer ├─ LLM fact-checks: is each claim supported by its source? ├─ Mark claims: SUPPORTED / UNSUPPORTED └─ Compute confidence score ↓ [Retry Gate] ├─ If grounded && used citations → DONE ✅ ├─ Else if retry_count < max_retries: │ ├─ Rewrite query (multi-query, CRAG) │ ├─ Fan out retrieval across variants │ └─ Retry from Retrieval Agent └─ Else → Return partial answer ⚠️

Corrective Retrieval & Augmented Generation (CRAG)

⚠️ When activated: If the Verification Agent flags claims as unsupported or no chunks were retrieved, the system doesn't just fail—it rewrites the query 2-3 times, retrieves again with all variants fused via Reciprocal Rank Fusion (RRF), and re-runs the entire Answer→Verify pipeline up to max_retries times.

Why this matters: A user asks "How do I install SearchUnify on Heroku?" but the corpus contains docs titled "Cloud Deployment Guide" (not "Heroku"). First retrieval returns zero results. CRAG rewrites to "Deploy SearchUnify to platform-as-a-service" → finds the right guide → generates an answer.

🤖 Agentic Components & Roles

The system is built on LangGraph, which orchestrates multiple specialized agents in a directed graph. Each agent is a stateless function that transforms the pipeline state.

1. Retrieval Agent

📍 retrieval_agent()

Input: Query string (and optionally query_variants from prior retry)

Action:

  • Calls hybrid_search() on OpenSearch
  • Combines BM25 score + dense vector similarity
  • Returns top-K hits (default K=10)
  • On retry loops: fuses results from multiple query_variants using RRF

Output State: retrieved: [{"content": "...", "url": "...", "title": "...", ...}, ...]

File: api/app/opensearch_client.py | hybrid_search(), reciprocal_rank_fusion()

2. Query Rewriting Agent (CRAG)

🔄 query_rewrite_agent()

Input: Original query, retry_count

Action:

  • Calls LLM with prompt: "Suggest 2-3 alternative phrasings of this question to find more relevant documents"
  • Generates query_variants e.g., ["...", "...", "..."]
  • Used by Retrieval Agent to run multiple retrievals + RRF fusion

Output State: query_variants: ["variant1", "variant2", ...]

File: api/app/graph.py | query_rewrite_agent()

3. Reranking Agent

⭐ reranking_agent()

Input: Retrieved chunks (from Retrieval Agent)

Action:

  • Loads cross-encoder model bge-reranker-base
  • Scores each (query, chunk_text) pair → [0, 1] relevance score
  • Sorts by score (highest first)
  • Keeps top-N (default: 3-5 chunks for context)

Output State: reranked: [{"content": "...", "rerank_score": 0.95, ...}, ...]

File: api/app/graph.py | reranking_agent()

4. Answer Agent

💬 answer_agent()

Input: Reranked chunks + original query

Action:

  • Builds numbered context: [1] (title — section)\n{chunk_text}\n\n[2] ...
  • Calls LLM with system prompt: "Answer ONLY using the numbered context. Cite sources inline like [1], [2]. If context doesn't contain the answer, say so explicitly."
  • Extracts inline citations [n] from response
  • Builds citation metadata (URL, title, section for each marker)

Output State: answer: "...[1]...[2]...", citations: [{"marker": "[1]", "url": "...", ...}, ...]

File: api/app/graph.py | answer_agent()

💡 Design Note: System prompt is deliberately strict: answers must be grounded in context, no hallucination. This ensures Verification Agent has a fighting chance to flag unsupported claims.

5. Verification Agent (Semantic Groundedness Check)

✅ verification_agent()

Input: Answer text + citations + reranked chunks

Action: Two-layer verification

Layer 1 — Syntactic:

  • Regex-scan answer for citation markers [n]
  • Check: does every [n] correspond to a reranked chunk?
  • Flag: unsupported_citations (if any)

Layer 2 — Semantic (NEW):

  • If Layer 1 passes, extract every cited sentence (e.g., "The API supports both REST and GraphQL [2].")
  • For each (claim, citations), build evidence by concatenating source chunks
  • LLM fact-check prompt: "For each claim, decide if it's fully supported by its evidence text. Respond: 'N: SUPPORTED' or 'N: UNSUPPORTED - reason'."
  • Parse LLM's per-claim verdicts
  • Flag: unsupported_claims (if any)

Output State:

{
  "grounded": true,                    # true if all checks pass
  "citations_used": ["[1]", "[2]"],   # which sources were cited
  "unsupported_citations": [],         # markers w/o chunks
  "unsupported_claims": [              # claims not supported by sources
    {
      "claim": "...",
      "citations": ["[2]"],
      "reason": "Evidence mentions ... but doesn't state ..."
    }
  ],
  "confidence": 0.95                   # 1.0 if grounded, else (1 - unsupported/total)
}

File: api/app/graph.py | verification_agent(), _semantic_groundedness_check()

6. Retry Gate

🔁 should_retry()

Decision Logic:

  • If retry_count >= max_retries → END (return answer as-is)
  • If verification is ungrounded (claims unsupported or no citations used) → RETRY
  • If no chunks retrieved → RETRY
  • Else → END (answer is good)

On RETRY: Increment retry_count, call Query Rewriting Agent, then Retrieval Agent again.

File: api/app/graph.py | should_retry()

Pipeline Graph Topology

START ↓ [retrieval_agent] ↓ [reranking_agent] ↓ [answer_agent] ↓ [verification_agent] ↓ [should_retry?] ◄─────────────────┐ / \ │ YES NO │ │ │ │ │ [END] ✅ │ │ │ [query_rewrite_agent] ─ rerun ──────────┘ ↓ [retrieval_agent] ...

State Management

The RagState TypedDict carries data through the pipeline:

class RagState(TypedDict, total=False):
    query: str                              # Original user query
    rewritten_query: str                    # CRAG rewrite (if retried)
    query_variants: list[str]               # Query variants from CRAG
    retrieved: list[dict]                   # Raw retrieval results
    reranked: list[dict]                    # Reranked chunks
    answer: str                             # LLM-generated answer with citations
    citations: list[dict]                   # Citation metadata [{"marker": "[1]", "url": "...", ...}]
    verification: dict                      # Verification output: grounded, confidence, unsupported_*
    retry_count: int                        # Number of retries so far

✅ Semantic Verification Deep Dive

The Problem

A syntactic check (does marker [n] exist?) can miss subtle failures:

  • Paraphrase drift: Answer says "Feature X is available" but source says "Feature X is not available in this tier" — marker is valid but claim is wrong
  • Scope mismatch: Answer claims "Supports all Salesforce editions" but source specifically lists "Console, not Communities"
  • Hallucinated detail: Answer says "Use API endpoint /v2/config" but source only mentions "config endpoint" without the path

The Solution: Semantic Groundedness Check

✅ How it works:
  1. Extract every sentence from the answer that contains a citation marker [n]
  2. For each cited sentence, compile evidence from its referenced chunk(s)
  3. Send (claim, evidence) pairs to the LLM with a strict fact-checking prompt
  4. LLM responds with "SUPPORTED" or "UNSUPPORTED - reason"
  5. Aggregate verdicts: answer is only truly grounded if 100% of claims are supported
  6. Confidence score = 1.0 if grounded, else (1 - unsupported/total)

Example: Verification in Action

Answer Generated:

"To configure Salesforce search, you must navigate to Browse MCPs, select SearchUnify, and click Configure [3]."

Semantic Verification Process:

Claim 1: "navigate to Browse MCPs"

Evidence from [3]: "Click Browse MCPs."

Verdict: ✅ SUPPORTED

Claim 2: "select SearchUnify"

Evidence from [3]: "Select Salesforce and click Continue... Select SearchUnify, and click Configure."

Verdict: ✅ SUPPORTED (document has both flows, the Required section indeed says "Select SearchUnify")

Final Result: 2/2 claims supported → grounded: true, confidence: 1.0

Performance Tuning

Parameter Impact Recommended Range
RERANK_TOP_K How many chunks are shown to answer + verify agents. ↑ more context, ↑ cost & latency. 3–5 (balance)
MAX_RETRIES How many times to retry if grounding fails. ↑ better coverage, ↑ latency. 1–3
VERIFY_EVIDENCE_MAX_CHARS Max evidence chars per claim to avoid token overflow in LLM. ↓ loses context. 1500–3000
ENABLE_SEMANTIC_VERIFICATION Disabling saves 1-2 LLM calls per query but loses grounding checks. true (recommended)

Deployment Scenarios

Local Development (CPU)

  • LLM: Ollama (local, CPU-friendly models like Mistral 7B, Gemma 7B)
  • Embedding/Reranker: BAAI models (CPU inference, slower but works)
  • Typical latency: 30–120 seconds per query (answer + verification)

Production (Cloud, GPU)

  • LLM: Groq (cloud hosted, sub-second latency) or local Ollama on GPU
  • Embedding/Reranker: BAAI models on GPU or cloud embeddings API
  • OpenSearch: Managed OpenSearch (AWS, Elastic Cloud)
  • Typical latency: 5–15 seconds per query

High-Volume System (Caching)

  • Cache embeddings + reranker scores for frequent queries (Redis)
  • Batch verification: queue verification jobs async, return partial answers immediately
  • Circuit breaker: fall back to /search (no LLM) if LLM latency exceeds threshold

✨ Key Features & Innovations

🎯 Corrective-RAG (CRAG)

Automatically rewrites queries if initial retrieval fails, combining multi-query + retrieval-fusion strategies.

📊 Hybrid Search

BM25 (keyword) + semantic (vector) retrieval unified via OpenSearch, capturing both lexical and conceptual matches.

🔍 Cross-Encoder Reranking

Neural reranker (bge-reranker-base) scores results by true relevance, not just embedding similarity.

✅ Semantic Verification

LLM fact-checks every claim against source text, catching paraphrase drift and hallucinations.

🔗 Inline Citations

Answers include [1], [2] markers with linked source URLs, titles, and sections.

📱 Dual Interfaces

REST API (for automation) + Streamlit web UI (for interactive exploration).

🔧 Troubleshooting & Common Issues

Empty Search Results

Symptom: User asks a question, retrieval returns 0 chunks.

Causes:

  • Corpus not indexed yet (run crawler + chunking first)
  • Wrong OpenSearch index name in config
  • Query language mismatch (e.g., asking in French but corpus is English)

Fix: Use /search endpoint to test hybrid search directly. Check OpenSearch index size: curl http://localhost:9200/searchunify_chunks/_stats

Low-Confidence Answers

Symptom: verification.confidence < 0.5 or unsupported_claims list is non-empty.

Cause: Answer Agent made claims not actually in the retrieved chunks (hallucination despite system prompt).

Fix:

  • Increase RERANK_TOP_K to give Answer Agent more context
  • Check if corpus contains relevant docs (via /search)
  • If still failing, system will auto-retry (CRAG) with rewritten queries

Slow Latency

Symptom: /ask request takes >2 minutes.

Causes:

  • CPU-only inference (embedding/reranker/LLM) is inherently slow
  • Semantic verification adds 1–2 extra LLM calls per query
  • Retries (CRAG) multiply latency

Fix:

  • Use GPU-accelerated inference if available
  • Switch to Groq (cloud LLM) for instant latency
  • Disable semantic verification temporarily: ENABLE_SEMANTIC_VERIFICATION=false
  • Reduce RERANK_TOP_K (trade off answer quality for speed)

LLM Not Responding

Symptom: API hangs when calling /ask.

Cause: Ollama not running or not reachable.

Fix: curl http://localhost:11434/api/tags to check Ollama. Start it: ollama serve
